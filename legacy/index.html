An array is a value. A slice is a view.

[5]int is forty bytes of data — assign it and you copy all of it. []int is a 24-byte header: a pointer, a length, and a capacity. Assign that and you copy the header, and both copies point at the same array.

Almost every slice surprise follows from that one fact. append writes into the backing array when there is capacity spare, and allocates a fresh one when there is not — so whether two slices stay connected depends on a number you usually are not looking at.

The three-index fix

s[1:3:3] sets the capacity as well as the bounds. Now len == cap, so the very next append is forced to allocate instead of writing into someone else's memory. This is what you want whenever you hand a sub-slice to code you do not control.

Swiss tables

Go 1.24 replaced the old bucket-and-overflow-chain map with a Swiss table. Slots are grouped 8 at a time, and each group carries a control word: one byte per slot holding either “empty”, “deleted”, or the top 7 bits of that slot's hash.

Those 8 control bytes pack into a single uint64. So the lookup compares your hash against all 8 slots with a handful of integer operations and no branches at all — then only touches actual keys for slots that already matched.

Why iteration order is random

It is deliberate. The runtime starts each range at a random group and a random slot, so you cannot come to depend on an order that was never guaranteed. Sort the keys if you need determinism.

Bytes, with a promise

A string is a pointer and a length, and the bytes it points at are immutable. That is what makes strings cheap to pass around and safe to share: slicing one is just another header over the same memory, with no copy and no allocation.

Immutability is also why []byte(s) has to allocate. The runtime cannot hand out a mutable view of memory it has promised nobody will change.

len is not length

len(s) counts bytes. Indexing gives you a byte. Only range decodes UTF-8 and yields runes — which is why its index jumps from 8 straight to 11 across a three-byte character.

Alignment costs bytes

Every type has an alignment, and a field's offset must be a multiple of it. An int64 has to start on an 8-byte boundary, so a bool sitting just before one leaves seven bytes of nothing behind it.

The compiler never reorders your fields — Go guarantees the layout you wrote. Which means the padding is yours to fix, and the fix is free: declaring the same fields largest-first can cut the struct by a third with no change in behaviour.

When it actually matters

For one struct, never. For a slice of a million of them, 24 bytes versus 16 is 8 MB of memory and a third more cache lines touched on every pass. go vet does not check this; fieldalignment in go tool's analysis suite does.

    Why it matters

    Goroutine stack free, dies at return
    →
    Heap costs a GC scan

    Where does it live?

    Go has no new/delete distinction you control. The compiler decides stack or heap by asking one question: can a pointer to this value outlive the frame that made it?

    It builds a directed graph of pointer flows and looks for a path from a value to a location that outlives the function — a return value, a global, a heap object, or a parameter of an un-inlined call. Reachable means heap.

    The payoff

    Stack allocation is a pointer bump and a free unwind. Heap allocation costs an mcache lookup now and GC marking later. This is why Go can feel like a value language despite pointers being everywhere.

    Two words, always
    
        
    An interface value is exactly two pointers wide. eface (the empty interface)
        holds a type descriptor and a data pointer. iface holds an itab and a data pointer.
    
        
    The itab is the join of an interface type and a concrete type: it caches the method
        addresses in a flat array, so a dynamic call is a load and an indirect CALL —
        not a hash lookup.
    
        
    
          
    The allocation nobody expects
    
          
    The data word is a pointer. Putting a value bigger than one word into an
          interface must box it on the heap. var s Shape = Rect{3,4} allocates 16 bytes
          unless the compiler can prove it escapes nowhere.

    G, M, P
    
        
    G is a goroutine: a stack plus saved registers. Cheap — 2 KB to start.
    
        M is an OS thread. Expensive, and blocked by syscalls.
    
        P is the right to run Go code. There are exactly GOMAXPROCS of them.
    
        
    P is the piece people miss. It is the scheduling context that owns a run queue and an
        mcache. An M must hold a P to execute Go — so P is the throttle that keeps
        parallelism at GOMAXPROCS even when thread count spikes.
    
        
    
          
    Watch for
    
          
    Work stealing. An idle P raids a random victim for half its queue.
    
          Handoff. A syscall detaches the P after ~20 µs so the other work keeps moving.
    
          The 61st tick. Every 61st schedule checks the global queue, so it can never starve.

    Stacks that grow
    
        
    A goroutine starts with a 2 KB stack — which is why a million of them fit in memory.
        It cannot be a fixed guard page, because it has to grow.
    
        
    So the compiler opens every non-leaf function with a bounds check against
        g.stackguard0, held in R14 on amd64. Fail it and you land in
        morestack → newstack: allocate double, copy the frames, and
        rewrite every pointer that aimed into the old stack. Then re-run the call as if
        nothing happened.
    
        
    
          
    The cost of moving
    
          
    Pointer adjustment is why Go stacks must be precisely typed and why
          uintptr is dangerous: the runtime can find and fix a *T, but a
          uintptr is just a number it will silently leave stale.

    Three defers, three costs
    
        
    Open-coded (Go 1.14+) is the fast path: when a function has at most 8
        defers and none in a loop, the compiler drops the calls straight into the return path and
        tracks which ones are live in an 8-bit register mask. Cost: near zero.
    
        
    Stack-allocated _defer records handle the rest of the
        straight-line cases. Heap-allocated ones are for defers inside loops,
        where the count is not known until runtime.
    
        
    
          
    How recover actually works
    
          
    recover() is not magic control flow. It marks the current _panic
          recovered and returns its argument. gopanic then calls mcall(recovery),
          which resets SP and PC to the deferring frame's return point — so the function returns
          normally, having never finished its body.

    A mutex, a ring, two queues
    
        
    A channel is a plain struct behind a lock: a ring buffer of dataqsiz slots,
        a send index, a receive index, and two waiting lists of sudog — one
        goroutine per blocked party.
    
        
    The interesting part is what doesn't happen. On an unbuffered channel the value
        never touches the buffer: send copies it straight from the sender's stack into
        the receiver's, then marks the receiver runnable. One copy, no queue.
    
        
    
          
    select, precisely
    
          
    selectgo shuffles a poll order with cheaprand (so no case is
          favoured), locks every channel in address order (so no deadlock), then sweeps twice:
          once looking for a ready case, and if none, parking the goroutine on all of
          them at once.

    Three tiers, one lock avoided
    
        
    Go's allocator is a thread-caching allocator in the TCMalloc family, rebuilt around P.
        Because the mcache hangs off the P and an M must hold a P to run Go code, the
        common allocation path needs no lock at all.
    
        
    Objects are rounded up to one of 68 size classes. That wastes a little memory (at most
        12.5%) and buys a lot: every object in a span is the same size, so the sweeper can free by
        clearing a bitmap instead of walking a list.
    
        
    
          
    The tiny allocator
    
          
    Pointer-free objects under 16 bytes get bump-packed into a shared 16-byte block.
          A bool, a small struct, a one-rune string — many land in the same word
          and cost nothing to sweep separately.

    Tricolour, concurrent, no compaction
    
        
    Everything starts white. Roots go grey.
        Scanning a grey object greys its children and turns it black.
        When no grey remains, white is garbage.
    
        
    The mutator is running the whole time, which breaks the invariant the moment a program
        stores a white pointer into a black object. Go's hybrid write barrier
        shades both the old value and the new one on every heap pointer write.
    
        
    
          
    Why the hybrid barrier mattered
    
          
    Shading the deleted pointer too means a goroutine's stack, once scanned, can never
          again hold an unscanned pointer. That removed the stack re-scan from mark termination and
          took stop-the-world pauses from tens of milliseconds to well under 100 µs.
